## Window scaling

Problem: the raylib window was fixed at 1024×768 and the maximise button was
disabled; menus were laid out for 1024 and anchored top-left; on a 16:9 monitor
there were black bars.

- New `src/grim/letterbox.py` — the frame renders to an off-screen target at a
  **virtual resolution that tracks the window's aspect ratio** (locked on the
  shorter axis to the configured base size) and blits to fill the whole window.
  No bars, no distortion, resizable / maximise / fullscreen all work.
- `rl.get_screen_*` / `rl.get_render_*` / `rl.get_mouse_*` are patched to virtual
  space so the world renderer, HUD, menus and mouse aim all follow.
- Every patched accessor derives its result **live from the current window
  size** each call — fixes an intermittent "mouse snaps to the bottom-left
  quadrant" caused by (a) a stale per-frame scale factor after a resize and
  (b) clamping the mapped cursor to a window corner when it left the window.
- `src/grim/app.py` `run_view(virtual_size=, on_virtual_resize=)`;
  `src/grim/terrain_render.py` defers ground baking while the letterbox target
  is open (avoids nested `begin_texture_mode`).
- `src/crimson/game/runtime.py` keeps `cfg.display` in step with the virtual
  size and keeps `FLAG_WINDOW_RESIZABLE`.
- Tests: `tests/grim/test_letterbox.py`.

# Dev log — 2026-09-08 (follow-up session)

Continued on `feat/roguelite-weapons`, on top of `6c964517b` / `6a3c3ac0f`.

## Landed

### Score-screen crash (`ReplayCheckpointsError`)
`_record_replay_checkpoint` (`modes/base_gameplay_mode.py`) only skipped an exact
duplicate of the last recorded tick. The `X` debug XP-grant / level-up spam pokes
player state off-tick and fed the recorder an out-of-order tick, which the
checkpoint format validator hard-rejects at the game-over save
(`checkpoint tick indices must be strictly increasing and unique`). Now it drops
any checkpoint whose tick is `<=` the last one. Verified: died after spamming
`X` + perks, score screen renders and the replay saves.

### Top bar removed / weapon icon relocated (`ui/hud.py`)
- `HUD_TOP_BAR = False` — the `ui_game_top` background strip is no longer drawn.
- `HUD_WEAPON_TL_*` — for single-player with the bar off, the weapon icon parks
  in the top-left corner on its own black backing box, full opacity.

### Player HUD font bump (`grim/fonts/small.py`, `render/world/player_status.py`)
- `draw_small_text` / `measure_small_text_width` gained an optional `scale`.
- The on-player clip ammo and power-up seconds render at `_HUD_TEXT_SCALE = 1.2`
  (one notch over the 16px default; the earlier view-scaled multiplier was too
  big and was reverted).

### `cfg.display` drift fixed (`game/runtime.py`)
Root cause of the ballooning virtual resolution: `_on_virtual_resize` writes the
runtime virtual size into `cfg.display.width/height`, and `config.save()` (called
on death and menu transitions) persists it - so every session read its own last
window-aspect size back as the *base*, and it compounded (found `crimson.cfg` at
`1679x898`). Fix:
- The letterbox base is now a fixed `1024x768`, never read from `cfg.display`.
- OS window size comes from `--width/--height` or the saved pref, sanitised to a
  1280x960 fallback if the cfg value is out of a sane range.
- Reset the corrupted local `artifacts/runtime/crimson.cfg` (not tracked).

### DPI awareness (`grim/app.py`)
`run_view` now calls `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` (with
`SetProcessDpiAwareness` / `SetProcessDPIAware` fallbacks) before `init_window`.
On this machine (3840x2160 display, Windows display scaling) a DPI-unaware
process was getting its window virtualised: raylib rendered at the requested
size and Windows bitmap-scaled the output to the screen (blurry), and
`GetMousePosition` / `GetScreenWidth` ended up in different unit spaces.

### Blade power-up debug view (`render/world/blades.py`)
Under `--debug`: a cyan circle for the orbit path (`BLADE_RADIUS`), a red circle
for each blade's contact hitbox (`BLADE_HIT_RADIUS`, before the per-creature
size term), and a yellow centre dot per blade.

### Debug overlay readout (`modes/survival_mode.py`)
Under `--debug`, a new line: `mouse virt=(x,y) raw=(x,y) vsize=WxH  weapon=<name>
ammo=n/clip` - so mouse drift and weapon-pickup behaviour can be read off-screen.
`grim/letterbox.raw_mouse_position()` exposes the unpatched cursor.

## Open / needs more work

### Mouse still drifts to the lower-left
Even after the earlier "don't clamp + recompute live" fix, the reticle
occasionally jumps. With the new debug readout the user saw it land at virtual
**`(187, 457)`** once, and another point near it. Very likely the DPI unit-space
mismatch described above (raw cursor in one space, window size in another,
letterbox divides one by the other -> cursor confined to a fraction of the
screen). The `SetProcessDpiAwarenessContext` change should address it; needs
confirmation on the user's machine, and if it persists, `_mouse_virtual` in
`grim/letterbox.py` should map from `get_render_width/height` (physical
framebuffer) rather than `get_screen_width/height`.

### "Music / sound screwed up"
Reported after several sessions. A fresh launch shows a clean WASAPI/miniaudio
init (18 streams, no errors), and the debug FPS logging showed a solid 60 fps
even at the (then still ballooned) virtual resolution, so it is not an obvious
frame-time / starvation issue. Possibly downstream of the DPI double-upscale on
the integrated GPU, or the ballooned virtual res, or environmental. Awaiting a
description of *how* it sounds (stutter / distortion / pitch / silence).

### Splitter Gun picked up but weapon didn't change
User reported the Splitter Gun (id 29) ground pickup not swapping their weapon.
`apply_weapon` -> `weapon_assign_player` has no guard, so it should equip;
`MY_FAVOURITE_WEAPON` (perk 48, from the `F3` spam) blocks weapon *pickups* and
is the likely explanation, but the new debug `weapon=` readout will confirm
whether the id actually changes on pickup.
